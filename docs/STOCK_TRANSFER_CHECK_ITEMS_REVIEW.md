# check_items review — 2026-09-29

Static review only: no sync action or database write was executed, and application code was not changed.

## Entry points

`POS.stock_transfer.Dlg_new_stock_transfer.check_items()` (line 4328) is called by jButton9 (line 1923). It reads the JVM main_branch property and opens either Dlg_inventory_cloud_transactions_main or Dlg_inventory_cloud_transactions_local modally. It passes no selected transfer or item list. This is whole-catalog synchronization, not transfer quantity/availability validation.

Main branch: dialog initialization calls check_for_upload; inventory rows marked is_uploaded=0 are queued for insert, rows marked 2 for update. Assembly membership is compared by main_item_code + item_code. Confirmation uploads inventory and applies assembly additions/deletions to the cloud.

Local branch: initialization loads all inventory and assembly rows from both databases. Missing local barcodes become additions, selected field differences become updates, and local barcodes absent from the cloud become deletions. Confirmation inserts, deletes, then updates locally. receipt_printing_enabled2 determines the update variant and whether assembly changes are applied.

A second method with the same name is in Dlg_new_stock_transfer_cloud_transactions (line 1151). It starts a SwingWorker that calls select_transaction. Column 5 loads the selected transfer's items; column 6 returns the selected transfer and the currently displayed item list.

## Prioritized findings and improvements

1. **Local deletion scope needs explicit review.** Local dialog lines 529–538 queue every local-only barcode. Lines 675–677 execute deletion. Inventory.delete_inventory (2488–2521) deletes inventory, inventory_barcodes, and assembly rows where the item is the parent. Thus an intentional branch-only item, or a legitimately empty/wrong cloud catalog, can cause local catalog removal. SQL failures throw; this finding does not assume a failed SELECT returns an empty list. Display deletion/assembly counts and an item preview, verify the authoritative catalog, and prefer explicit tombstones/archive policy over absence-based deletion.
2. **Errors are hidden and UI threading is inconsistent.** Both dialogs query during initialization on the button's Swing event thread. Background workers later update Swing labels directly, and done() never calls get(), so exceptions are not surfaced there. Move reads/comparisons into a typed worker, return immutable results, render on the event thread, call get() in done() with visible failure handling, and prevent overlapping operations.
3. **Assembly edits are missed.** Main dialog 449–475 and local dialog 462–490 compare membership only. A changed quantity, unit, conversion, or other synchronized field on an existing component pair is not queued for an assembly update. Add a field comparison and update operation for matching keys.
4. **Item comparison is inconsistent with writes.** Local dialog 507–520 checks selected fields but excludes fields such as cost, supplier, category IDs and show_to_sales that may be meaningful to synchronize. Barcode equality is case-sensitive for additions (496) but case-insensitive for deletions (532). Define the synchronized fields and identity/case rules once; use the same rules for comparison and persistence. Match database collation and reject duplicate identities before choosing a uniqueness constraint.
5. **Price policy is obscure.** Local dialog 683–699 uses receipt_printing_enabled2 to decide price/assembly behavior. Inventory.edit_inventory_no_price still updates inventory.selling_price (1578, 1619), while its inventory_barcodes update omits selling_price. Therefore its name does not mean all local prices are preserved. Define whether master and location prices should differ, then use dedicated sync policy settings instead of a printing switch.
6. **Catalog matching is quadratic.** Nested scans compare every cloud item against local items and then reverse the scan; assemblies do likewise. Build maps by barcode and composite assembly key for expected O(local + cloud) matching, explicitly reporting duplicate/null keys. This reduces comparison cost but not the full-table network load; paging or version-based deltas can follow.
7. **Connection lifecycle and retry behavior need work.** Inventory.ret_data22_cloud (2734–2835) leaves its connection, statement and result set open. Per-item writes commit independently, so an interruption can leave a partial sync. Close owned JDBC resources deterministically, use bound parameters rather than concatenated barcode predicates, and design idempotent writes/checkpoints. Snapshot indexes show only an id primary key on inventory and inventory_assembly; do not assume barcode uniqueness is enforced. A single local transaction cannot make writes to two separate database servers atomic.
8. **Cached dialogs can display stale plans.** create() returns a previously cached instance, while the comparison is run from myInit and after writes. The stock-transfer opener does not explicitly refresh when reopening. Refresh on every opening and revalidate before applying a plan.
9. **The other check_items can return mismatched transfer/items.** In cloud transactions, select_transaction lines 809–815 uses the selected transfer header plus the existing shared item model without verifying that the list belongs to that header. Load A's items using column 5, then choose B using column 6: A's items can accompany B. Capture the transfer ID on the event thread, fetch its own items, and return a copied list tied to that ID. Avoid reading mutable table selection from the worker.

## Suggested implementation order

First protect correctness: transfer/item identity, deletion preview/policy, worker error handling, and refresh. Next separate a pure comparison service from database reads/writes, with explicit field and price policies. Then add map-based comparison, assembly updates, resource cleanup and retry-safe persistence.

Useful regression scenarios: unchanged catalogs; add/update only; empty cloud catalog; branch-only item; assembly quantity-only edit; case-differing/duplicate barcodes; price policy on/off; cloud exception mid-run; reopened dialog; and selecting transfer B after loading A. Use in-memory comparison fixtures and an isolated database for write-path tests.
